# Как устроен поисковый робот

Этот документ объясняет всё с нуля: что делает робот, где лежат данные, что происходит при остановке и как читать код. Код робота — [crawler/crawler.py](../crawler/crawler.py), около 140 строк.

## Зачем он нужен

Поисковому движку нужен корпус — набор документов, по которым потом будем искать. Робот собирает этот корпус: скачивает статьи о фильмах и сериалах из русской Википедии и Викицитатника и складывает их HTML в MongoDB как есть.

Что требует задание и как это сделано:

| Требование | Как сделано |
|---|---|
| Единственный аргумент — путь до yaml-конфига | `python crawler/crawler.py crawler/config.yaml` |
| Секция `db` с данными базы | `db.uri`, `db.name` |
| Секция `logic` с задержкой между страницами | `logic.delay_seconds` |
| В базе: нормализованный url | поле `url`, функция `normalize_url` |
| В базе: «сырой» HTML | поле `html` |
| В базе: название источника | поле `source` (`wikipedia` или `wikiquote`) |
| В базе: дата обкачки в Unix timestamp | поле `crawled_at` |
| Можно остановить в любой момент и продолжить с того же документа | очередь и прогресс хранятся в MongoDB, а не в памяти |
| Периодически переобкачивать документы, но только изменившиеся | раз в `recrawl_seconds` условный запрос `If-Modified-Since`; ответ `304` — не изменилась |

## Из чего состоит проект

```text
crawler/
  crawler.py        сам робот
  config.yaml       настройки: база, задержка, источники
  test_crawler.py   автотесты
compose.yaml        MongoDB и веб-интерфейс к ней (mongo-express) в Docker
requirements.txt    Python-библиотеки: requests, PyYAML, pymongo
```

## Как запустить

```bash
docker compose up -d                                   # поднять MongoDB и mongo-express
python -m venv .venv                                   # один раз: создать окружение
.venv/bin/pip install -r requirements.txt              # один раз: поставить библиотеки
.venv/bin/python crawler/crawler.py crawler/config.yaml
```

Остановить робота — **Ctrl+C**. Продолжить — та же последняя команда.

Посмотреть, что скачалось: http://localhost:8081 → база `search_engine` → коллекция `documents`.

## Конфиг по строчкам

```yaml
db:
  uri: mongodb://127.0.0.1:27017    # где MongoDB
  name: search_engine               # имя базы внутри MongoDB

logic:
  delay_seconds: 1                  # пауза перед каждым запросом к сайту
  recrawl_seconds: 86400            # через сколько секунд перепроверять страницу (сутки)
  user_agent: MAI-IR-crawler/1.0 (https://github.com/...)   # как робот представляется сайту

sources:                            # откуда качать
  - name: wikipedia                 # это имя попадёт в поле source документа
    url: https://ru.wikipedia.org
    categories:                     # какие категории статей обойти
      - Категория:Фильмы по алфавиту
      - Категория:Телесериалы по алфавиту
  - name: wikiquote
    ...
```

`user_agent` важен: Википедия требует, чтобы бот указывал, кто он и как с ним связаться. С безымянным User-Agent она быстрее начинает отвечать «слишком много запросов».

## Что лежит в базе

В базе `search_engine` три коллекции. Проще всего понять их через аналогию с библиотекарем, который составляет картотеку.

### `documents` — результат, ради которого всё затевалось

Одна запись — одна скачанная статья:

```json
{
  "url": "https://ru.wikipedia.org/wiki/%D0%98%D0%BD%D1%82%D0%B5%D1%80%D1%81%D1%82%D0%B5%D0%BB%D0%BB%D0%B0%D1%80",
  "html": "<!DOCTYPE html><html ...>... вся страница ...</html>",
  "source": "wikipedia",
  "crawled_at": 1791483605
}
```

`crawled_at` — когда HTML был скачан, в секундах с 1 января 1970 года. Если при перепроверке страница не изменилась, запись не трогается, и `crawled_at` остаётся датой настоящего скачивания.

Именно эту коллекцию будут читать следующие лабораторные: токенизация, индекс и так далее.

### `frontier` — очередь «что скачать и когда»

Это список дел робота. Одна запись — одна статья, которую надо скачать или перепроверить:

```json
{
  "url": "https://ru.wikipedia.org/wiki/...",
  "source": "wikipedia",
  "next_crawl": 1791570005,
  "last_modified": "Wed, 07 Oct 2026 10:55:45 GMT"
}
```

- `next_crawl` — когда браться за страницу. У новой страницы это `0`, то есть «прямо сейчас». После обработки — «сейчас + сутки».
- `last_modified` — дата изменения страницы, которую сайт сообщил при последнем скачивании. Нужна, чтобы при перепроверке спросить «изменилась ли страница с этой даты?».

В `frontier` хранится всё служебное, поэтому в `documents` остаются только поля, которые требует задание.

### `categories` — закладки в списках категорий

Одна запись — одна категория одного сайта:

```json
{
  "_id": "wikipedia:Категория:Фильмы по алфавиту",
  "continue": {"gcmcontinue": "page|...|7062567", "continue": "gcmcontinue||"},
  "done": false,
  "listed_at": 1791483000
}
```

- `continue` — закладка: где мы остановились в списке статей категории. Это непонятная строка, которую выдаёт сама Википедия, и робот просто отдаёт её обратно.
- `done` — категория пройдена до конца.
- `listed_at` — когда последний раз получали пачку из этой категории. Нужно, чтобы через сутки пройти категорию заново и найти новые статьи.

## Как робот работает, по шагам

Вся работа — бесконечный цикл из «проходов». Один проход выглядит так:

```text
┌─ ПРОХОД ──────────────────────────────────────────────────────────────┐
│ 1. Для каждого сайта:                                                  │
│      скачать robots.txt                                                │
│      для каждой категории: дособрать список статей → в очередь         │
│ 2. Запомнить время начала прохода                                      │
│ 3. Пока в очереди есть страница, которой «пора» на момент начала:      │
│      скачать или перепроверить её, назначить следующую проверку        │
│ 4. Поспать до ближайшей следующей проверки                             │
└──────────────────────────────────────────── и снова на шаг 1 ─────────┘
```

Разберём каждый шаг.

### Шаг 1. Собрать список статей (`discover`, `discover_category`)

Сначала робот читает `robots.txt` сайта. Это файл, где владелец сайта пишет, какие страницы роботам качать нельзя. Каждую найденную статью робот проверяет по этому файлу, и запрещённые в очередь не попадают.

Потом робот спрашивает у Википедии: «дай статьи из категории "Фильмы по алфавиту"». Для этого у Википедии есть специальный API — адрес `/w/api.php`, который отвечает не HTML-страницей, а JSON-данными. Важные параметры запроса:

- `generator=categorymembers`, `gcmtitle=...` — «перечисли статьи этой категории»;
- `gcmnamespace=0` — только обычные статьи, без подкатегорий, шаблонов и служебных страниц;
- `gcmlimit=max` — по максимуму за раз, это 500;
- `prop=info`, `inprop=url` — заодно сообщи адрес каждой статьи.

В категории 38 тысяч статей, а за раз дают 500. Поэтому ответ приходит пачками: в каждом ответе есть поле `continue`, то есть закладка «вот отсюда продолжай». Робот отправляет её в следующем запросе и получает следующие 500 статей. Если `continue` в ответе нет, категория закончилась.

После **каждой** пачки робот:
1. кладёт её адреса в очередь `frontier`. Если адрес там уже есть, запись не меняется, дубликатов не бывает (`upsert` + `$setOnInsert`);
2. сохраняет закладку `continue` в `categories`.

Поэтому, если остановить робота на середине категории, при следующем запуске он продолжит с сохранённой закладки, а не с буквы «А».

Пройденная категория (`done: true`) пропускается, пока не пройдут сутки (`recrawl_seconds`) с `listed_at`. После этого она проходится заново: уже известные статьи пропускаются, новые добавляются в очередь.

### Нормализация URL (`normalize_url`)

Один и тот же адрес можно записать по-разному:

```text
https://RU.Wikipedia.org/wiki/Матрица_(фильм)#Сюжет
https://ru.wikipedia.org/wiki/%D0%9C%D0%B0%D1%82%D1%80%D0%B8%D1%86%D0%B0_%28%D1%84%D0%B8%D0%BB%D1%8C%D0%BC%29
```

Это одна и та же страница. Нормализация приводит такие записи к единому виду, чтобы одна страница не попала в базу дважды под разными адресами:

- схема и домен — маленькими буквами;
- путь сначала раскодируется, потом кодируется заново. Например, кириллица и скобки всегда превращаются в `%D0%9C...`, `%28`, `%29`, а не остаются то так, то эдак;
- якорь `#Сюжет` отбрасывается: это место на той же странице, а не другая страница.

### Шаг 2–3. Скачать страницы (`run`, `crawl`)

Робот берёт из очереди страницу с наименьшим `next_crawl`. Если таких несколько (например, все новые с `0`), берёт ту, что попала в очередь раньше. Так он идёт по очереди сверху вниз.

Для каждой страницы (`crawl`):

1. Если страницу уже скачивали, в запрос добавляется заголовок `If-Modified-Since: <last_modified>` — «отдай страницу, только если она менялась после этой даты».
2. Запрос к сайту:
   - ответ **`304 Not Modified`** — страница не менялась. Робот ничего не сохраняет, в логе пишет `не изменилась`;
   - ответ **`200 OK`** — страница новая или изменилась. Робот записывает её в `documents` (или перезаписывает старую версию), запоминает новый `Last-Modified`, пишет в лог `скачана`.
3. В любом случае странице назначается `next_crawl = сейчас + сутки`, и она уходит в конец очереди.

Это и есть «переобкачивать, только если изменилась»: сайт сам говорит, менялась ли страница, и HTML скачивается, только если менялась. Википедия обновляет дату изменения и тогда, когда поменялся шаблон внутри статьи, а не только сам текст.

### Почему проход всегда заканчивается

На шаге 2 робот запоминает время начала прохода и в этом проходе берёт только страницы, которым «пора» на этот момент. Это важно. Весь обход длится около 26 часов, а перепроверка — через 24. Без этой отсечки к концу обхода уже «пора» перепроверять первые страницы, и робот никогда бы не вышел из шага 3, а значит, никогда бы не вернулся на шаг 1 искать новые статьи.

С отсечкой каждая обработанная страница получает `next_crawl` в будущем, новых страниц во время шага 3 не появляется, и список «кому пора» только уменьшается. Значит, проход обязательно закончится.

### Шаг 4. Подождать

После прохода робот смотрит, у какой страницы самая ранняя следующая проверка, и спит до этого момента. Если этот момент уже наступил (обход длинный), он не спит и сразу начинает новый проход.

### Вежливость: задержка (`get`)

Все запросы к сайтам идут через метод `get`. Перед каждым запросом он ждёт `delay_seconds`, чтобы не заваливать сайт запросами. Если сайт всё-таки отвечает **`429 Too Many Requests`** («слишком часто»), робот ждёт столько секунд, сколько сайт указал в заголовке `Retry-After` (если не указал — минуту), и повторяет тот же запрос.

## Что будет, если остановить робота

Всё, что робот знает, лежит в MongoDB и записывается сразу после каждого шага. В памяти нет ничего, что жалко потерять. Поэтому неважно, как его остановили: Ctrl+C, закрыли терминал, выключили компьютер.

| Где остановили | Что будет при следующем запуске |
|---|---|
| Посреди пачки из категории | Эта пачка запросится ещё раз. Адреса, которые уже лежат в очереди, не задублируются |
| Посреди скачивания страницы | У страницы ещё старый `next_crawl`, она первая в очереди, робот начнёт с неё |
| После сохранения документа, но до обновления очереди | Страница скачается ещё раз и перезапишет сама себя, дубликата не будет: `url` уникален |
| Во время сна между проходами | Ничего не потеряно, робот проверит, кому пора, и продолжит |

Запускать **два робота на одну базу одновременно нельзя**: они будут брать одни и те же страницы.

## Ошибки

| Что случилось | Что делает робот |
|---|---|
| `429` — сайт просит реже | ждёт `Retry-After` и повторяет запрос |
| `404`, `500` и прочие ошибки сервера на странице | пишет в лог `ошибка ...`, откладывает страницу на сутки, идёт дальше |
| Страница больше 16 МБ (лимит одного документа MongoDB) | то же самое: лог и откладывание. Для Википедии практически невозможно |
| Пропал интернет, сайт не отвечает 30 секунд | робот падает с ошибкой. После перезапуска продолжит с той же страницы |
| Ошибка во время сбора категорий | робот падает. После перезапуска продолжит с сохранённой закладки |

## Сколько это займёт

- В категориях около 46 400 статей: 43 300 из Википедии и 3 100 из Викицитатника.
- Сбор списков — 95 запросов к API, пара минут.
- Скачивание идёт примерно по 2 секунды на страницу (1 секунда паузы плюс ответ сайта), весь корпус — около 26 часов. Если поставить `delay_seconds: 0.5`, будет быстрее, но при `429` задержку лучше не уменьшать.
- Объём: HTML статьи — 100–700 КБ, всего около 9 ГБ. MongoDB сжимает данные, на диске будет в несколько раз меньше.

## Как посмотреть и поуправлять данными

Через браузер: http://localhost:8081.

Через командную строку:

```bash
# сколько документов скачано
docker compose exec mongo mongosh search_engine --quiet --eval 'db.documents.countDocuments()'

# сколько всего статей в очереди
docker compose exec mongo mongosh search_engine --quiet --eval 'db.frontier.countDocuments()'

# начать всё с нуля (удалит скачанное!)
docker compose exec mongo mongosh search_engine --quiet --eval 'db.dropDatabase()'
```

Данные хранятся в Docker-томе `mai-ir_mongo-data` и переживают `docker compose down` и перезагрузку компьютера. **`docker compose down -v` удаляет том вместе со всей базой.**

## Тесты

```bash
.venv/bin/python -m unittest discover crawler -v
```

Тесты не ходят в настоящую Википедию. Они поднимают у себя маленький поддельный сайт (`FakeWiki`): у него есть `robots.txt`, API с категорией из двух пачек и страницы статей, и он умеет отвечать `304`, `429` и `500`. Каждый тест работает в своей временной базе `test_*` и удаляет её после себя. Нужна запущенная MongoDB.

| Тест | Что проверяет |
|---|---|
| `test_normalize_url` | разные записи одного адреса нормализуются одинаково |
| `test_saves_documents_with_required_fields` | в документе есть `url`, `html`, `source`, `crawled_at` |
| `test_skips_pages_forbidden_by_robots` | страница, запрещённая в `robots.txt`, не скачивается |
| `test_resumes_category_listing_after_failure` | после сбоя сбор категории продолжается с закладки, а не с начала |
| `test_resumes_crawl_after_kill` | робота убивают посреди работы, после перезапуска он не качает заново готовое и докачивает остальное |
| `test_recrawl_keeps_unchanged_page` | неизменённая страница (`304`) не перезаписывается |
| `test_recrawl_updates_changed_page` | изменённая страница перезаписывается |
| `test_periodically_recrawls_changed_pages` | запущенный робот сам замечает изменение страницы через `recrawl_seconds` |
| `test_finds_new_pages_in_category_after_recrawl_interval` | запущенный робот сам находит новую статью в категории |
| `test_waits_and_retries_when_rate_limited` | на `429` робот ждёт и повторяет запрос, а не падает |

## Ограничения

- Берутся только статьи, лежащие прямо в указанных категориях, без подкатегорий. Категории «…по алфавиту» плоские, для них этого достаточно.
- Если статью удалят из Википедии, её старая версия останется в `documents`: робот получит `404` и просто будет откладывать её.
- Если статью уберут из категории, она останется в очереди и в базе.
- Один робот на одну базу.
